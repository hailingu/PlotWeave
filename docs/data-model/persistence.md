## 十、本地存储体系

**当前实现归属（2026-10-04 路线修订，[PR #526](https://github.com/hailingu/PlotWeave/pull/526)）**：原生应用由 `NativeHostServices.perform` 将项目 IPC 直接交给 Swift `NativeProjectStore`，已实现创建、列表、加载、保存、删除、AI 会话和资产验证／复制；不经过 Rust 或 C ABI。`NativeDirectory` 拥有句柄相对 no-follow I/O 与原子写，`NativeProjectEnvelope` 拥有信封校验、保存盖戳及摘要投影。Tauri 保留 `crates/plotweave-core/src/store/` 内核和 `src-tauri/src/store/mod.rs` 包装作为行为与磁盘合同回归基线。`crates/plotweave-ffi/` 为历史 P2 能力，未被原生工程链接；不能再用“尚待接入 C ABI”描述当前 Swift 保存状态。

### 10.0 Swift 原生落地与保留差异

**Web 写入与最终退出（[PR #526 R36–R37](../swiftui-react-flow-pr526-fixes.md#反向宿主请求退役与-web-最终退出协调)）**：Swift 正常退出同步暂停新 Web 输入／业务，既有异步操作完整交付并由实际 React effect 确认状态提交，再等待画布、项目链、AI 与设置／密钥四源固定点；同一同步跨度内确认业务及保存均空闲并封口，之后到原生批准期间持久化 owner 不接受新状态。失败恢复输入、保留最新失败稿并取消系统退出，明确重试可继续。项目创建／打开／重命名／复制／删除、模型回合、生图、资产导入与受保护异步重做都登记完整业务 future，不能只等待底层 IPC。Web→Swift 的规范身份在 4096 条窗口内只退役已完成结果；退役重放明确拒绝而不重复副作用，长期页的正常保存／退出不会因已完成结果累积永久耗尽。旧式 opaque 满载仍需真正重载页面；项目往返不重置，两方向缓存各自拥有水位。

| 责任／边界 | 当前 Swift 实现与保留范围 |
| --- | --- |
| 数据根与身份 | 根由宿主注入，Web 请求不能选择目录；开发根为 Application Support 下由 `BundleID + ".development"` 派生的 `dev.plotweave.PlotWeaveNative.development`。测试只用临时根；不自动读取 Tauri 数据或历史 Keychain，发行身份与数据迁移仍为独立决定。 |
| 项目布局与真源 | 权威文档为 `projects/{id}.json`；媒体与 AI 会话分别为 `projects/{id}/assets/`、`projects/{id}/ai-session.json`。首页每次扫描项目文档，不维护 `index.json`。§10.1 的 `{id}/project.json` 与索引布局仍是演进目标，不因 Swift 服务实现而视为完成。 |
| 会话与写入 owner | React 继续拥有图文档、撤销、防抖、保存／删除链和退出冲刷；Swift actor 串行执行项目保存、删除及项目媒体事务，`expectExisting` 在同一 actor 内拒绝删除后的迟到保存。原生界面不拥有可写文档副本。 |
| 文件提交与失败 | 原子写先同步临时文件，rename 后同步父目录；保存前后均按绑定目录句柄复验媒体。提交前拒绝保留旧文档；提交后目录同步或资产复验失败如实报错，新文档可能已经落盘，不保证回滚。两类失败的既有边界见 §10.5 与[资产 §7.1](assets.md#71-两个作用域)。 |
| 兼容性差异 | v1 文档、AI 会话与资产引用沿用既有格式；旧扁平 v0 格式支持已随 [#519 处置](https://github.com/hailingu/PlotWeave/issues/519)退役，两栈判型统一拒绝并保留原文件，此前记录的脏 legacy 小数 `updated_at` 排序差异不再存在。 |
| 验证缺口 | 单应用实例范围保持；不承诺跨进程媒体替换与文档之间的事务。原子写的系统调用故障注入（临时文件同步、rename、rename 后父目录同步）已随 [issue #543](https://github.com/hailingu/PlotWeave/issues/543) 由 Swift 测试验收，见下方验证记录；真实系统面板、IME、VoiceOver、视觉、性能与签名分发仍未验收，不能由隔离根测试推定通过。 |

详细落地与缺口见[总体分层](overview.md#二总体分层)、[功能补齐记录](../swiftui-react-flow-feature-parity.md)及[修复矩阵 R20–R21](../swiftui-react-flow-pr526-fixes.md)。下文明确标注 Tauri／Rust 的实现说明继续描述其基线，不意味着 Swift 调用这些内核；公共文档格式与失败语义仍适用于两条服务路径。

验证记录（2026-10-15，[issue #543](https://github.com/hailingu/PlotWeave/issues/543)）：Swift 原子写的系统 fsync／rename 故障注入已验收。测试专用 `NativeAtomicWriteFaults` 以互斥锁保护、绑定写入目录描述符的阶段注入包装真实系统调用（临时文件 `fsync`、提交 `renameat`／`renameatx_np`、rename 后父目录 `fsync`）——故障窗口只拦截登记目录的写入，并发执行的其他测试套件使用各自临时根与描述符，永不被拦截或计入阶段记录，不依赖运行器串行；与 Rust `store::persist::faults` 基线同级。生产路径无活动注入时按原样执行，不改变成功保存的文件布局、时间戳或 v0 拒绝行为。`NativeAtomicWriteFaultTests` 在隔离临时根上经 `save_project` 命令观察三类失败：临时文件同步与 rename 失败（提交前）——`PW_STORAGE_ERROR` 上浮、磁盘保持旧文档、无临时文件残留、注入撤除后重试收敛为新文档；rename 后目录屏障失败（提交后）——如实报错、新文档已落盘不回滚、重试幂等收敛。三阶段以「已抵达阶段」记录自证守卫（rename 前置于屏障）。注入为 errno 级阶段模拟（EIO），不等同真实断电实验；Tauri／Rust 基线故障测试保留，不替代本路径，也不被本路径替代。

历史 FFI `saveProject` 的可选布尔 `expectExisting` 沿用 Tauri 保存的存在性约束：缺省 `false` 保留初次创建，`true` 在共享操作锁内确认目标仍存在，删除后的迟到请求返回失败且不得重建项目；非法字段类型拒绝。保存 NotFound 不携带 `[project_not_found]` 码，该码仅由加载入口返回。调用方仍须维护项目保存/删除协调，FFI guard 不替代会话排序；兼容性回归见[P2 合并同步](../swiftui-react-flow-p2-evidence.md#dev-合并兼容性同步2026-10-04)。当前 Swift 在自己的 actor 内实现同一存在性约束，并未接入该历史调用路径。

Swift 正常退出的系统决定由 `NativeApplicationDelegate` 拥有：[PR #526](https://github.com/hailingu/PlotWeave/pull/526) 修复后，监听已就绪时保留 AppKit `terminateLater`，固定点冲刷成功回复 `true`，失败回复 `false` 并保留窗口、诊断和最新失败快照。仅 Swift 的既有 `app_exit` 增加可选布尔 `cancel`：`true` 幂等取消当前意图，不要求监听已就绪；缺省／`false` 保持成功批准，非法类型拒绝。Web 保存失败、抛错、批准失败和初始化失败均通过此信号完成取消；原生事件投递失败或替换已就绪页面也取消旧决定，已取消的旧投递不能拒绝新意图。当前连接的进程终止、导航失败、拆除、就绪超时或资源缺失经统一页面失效入口取消意图并撤销监听资格；弱 coordinator 身份约束阻止旧页迟到失败取消新页退出。已失效页面的启动缓冲同样清除，重载后须明确重试，见修复矩阵 R27。监听未就绪的系统请求先取消并缓冲启动意图，避免等待尚不存在的监听；成功系统序列继续原来的成功回复，不一律取消后重发。Tauri 载荷与磁盘合同保持；取消信号自身失败须同时保留原错误与取消诊断。真实 Dock／菜单手势和系统注销仍待人工验收。

命令产出的文档变更，经防抖持久化回调落到以下布局。

原生表单的 `send` 和 awaitable `request` 在当前页同步登记在途意图；退出先等待这些请求完成，再投递 Web 保存固定点屏障。请求失败取消本次退出，不自动重做；最终批准仍有冲刷期间新增的原生意图时，以 `PW_NATIVE_INTENTS_PENDING` 拒绝并保持可重试窗口，下一次明确退出重新冲刷。页面更新／失效撤销旧任务归属，取消后的旧投递不会重放退出。该顺序保护尚未跨桥或仍等待 fingerprint 的最后编辑，未将原生表单升级为可写文档 owner；矩阵与真实磁盘证据见 [PR #526 R29](../swiftui-react-flow-pr526-fixes.md#原生意图进入退出屏障)。

### 10.1 目录布局

```
应用数据目录/                           # Tauri app_data_dir，禁止硬编码路径
├── projects/
│   └── {projectId}/
│       ├── project.json               # ProjectDocument
│       ├── ai-session.json             # AI 创作历史（独立 schemaVersion）
│       └── assets/                    # 项目资产（自包含）
│           ├── {assetId}.png
│           └── {assetId}.mp4
├── library/                           # 个人资产库（跨项目复用）
│   ├── library.json                   # 库索引：assets.byId（分类/视角/标签）+ groups.byId（编组）
│   ├── asset-delete-journal.json      # 删除事务与折叠统计：{entries:[…],retainedCleanupCount:N,trashBytes?:B}（issue #421）
│   ├── asset-delete-archive.json      # 旧旁路统计；仅数组日志/日志缺失时读取，迁移后保留但不再读写
│   └── assets/
│       ├── {assetId}.png
│       └── .trash/                    # 随机名私有隔离区；禁止进入任何 AssetRef
├── index.json                         # 项目索引：首页列表元数据（id/名称/缩略图/updatedAt）
└── settings.json                      # AppSettings：provider 配置与模型选择（不含 API key）
```

删除日志兼容迁移（issue #421）见 [§7.2 联合统计矩阵](assets.md#删除日志联合统计状态与不变量矩阵issue-421)：旧数组日志或仅旧旁路统计在首次完整日志写入时迁移，健康库在日志与旧旁路均缺失时正常读取无需创建空日志（`missing_journal_without_legacy_totals_needs_no_write` 先红后绿）。极接近 1 MiB 的旧日志可能因对象头部使迁移超过写入上限；该写入拒绝保留事务条目和媒体字节，既有上限不扩大。

**存储布局迁移（独立于文档 schema 迁移的轴）**：文档 `schemaVersion` 迁移（§11.1）只转换文档内容，不涉及文件位置。当前实现（v1 文档）均以扁平 `projects/{id}.json` 存储——上文目录布局中的每项目子目录、`assets/` 与 `index.json` 随 §7.1 项目资产落地。届时**必须**三选一，防止既有项目在首页消失：

- **布局迁移**：启动时发现旧扁平文件 → 建目录搬移为 `{id}/project.json` → 写入 `index.json`，迁移原子完成（失败回滚到扁平布局）；
- **路径回退**：目录化后 `list_projects`/`load_project` 仍兼容发现扁平旧文件（只读兼容，首次保存时搬移）；
- 或两者结合（推荐：启动迁移 + 兜底回退）。

布局迁移未实现前，§10.1 的 `index.json`/每项目目录不应成为 `list_projects` 的唯一数据源。

**AI 会话存储（[issue #47](https://github.com/hailingu/PlotWeave/issues/47)、[PR #57](https://github.com/hailingu/PlotWeave/pull/57)，已实现）**：会话独立保存在 `projects/{id}/ai-session.json`，`schemaVersion: 1` 保存消息 id、角色、顺序、正文及预览卡/执行回执。落盘总条数最多 200 条（[issue #64](https://github.com/hailingu/PlotWeave/issues/64)、[PR #85](https://github.com/hailingu/PlotWeave/pull/85)，已实现）：可执行待执行卡（`pending` 且校验通过，含自未确认执行卡降级来的）优先占用容量，其余额度保留最新历史，最终按原时间线输出。待执行卡自身超过 200 张时也从最旧提案起裁剪，不再额外追加无上限的钉住卡；最多 200 张时，继续普通聊天不会挤掉待执行卡。校验拒绝卡、已执行及已忽略卡按普通历史处理。此规则限制条目数量，不承诺文件字节上限；待执行卡占满容量时普通历史可能全部不落盘，超额旧提案重开后不再恢复（状态矩阵及边界见 [UI 设计 §6.2](../ui-design.md#62-会话落盘总量回归矩阵issue-64)）。裁剪只发生在写入主文件的落盘边界（前端 `aiSessionStore` 的 `diskSessionOf`，浏览器内存回退同语义）：面板保存通道与进程内快照（设置页重挂载种子、保存失败保留、退出冲刷待写重试）持全量落盘形态，设置页往返与失败后重开不丢进程内历史；内存线程与加载归一化都不裁剪（旧文件全量展示，下次实际变更保存才收敛）。缺文件返回空历史；前端逐条归一化并隔离坏条目。JSON 或信封损坏返回 `{ session: null, corrupt: true }`，界面显示损坏诊断；真实 I/O 读取失败仍返回错误。两者都不阻断画布打开。真实 I/O 读取失败时，AI 操作区只显示诊断并停用发送与执行，重开项目成功读取后才恢复；缺文件仍可正常开始聊天。损坏诊断不触发自动写回，后续实际编辑保存成功才更新主文件。

**范围决定（2026-09-10，仓库所有者确认）**：本项目按单应用实例使用，不考虑多实例或跨进程并发。AI 会话不维护跨进程文件锁、写入序号、冲突检测或历史分叉合并，也不新增单实例插件。只有主文件一个持久化来源；保存失败上浮给面板并保留进程内历史，不创建、读取、提升或清扫恢复副本，不进行定时自动重试。这一决定取代 PR #57 早期双副本恢复协议。旧开发版本主文件里的 `writeSeq` 不再参与保存判定；旧开发版本恢复目录不作为数据源，也不自动迁移或删除。

同一项目的会话写入复用保存/删除串行链，主文件使用同目录临时文件、flush、原子 rename 与父目录同步。失败的最新快照保留至成功保存或删除项目；后续消息变更、重开保留会话、再次尝试退出均可重试主文件。正常关闭窗口、macOS ⌘Q 与 Dock「退出」共用应用级退出屏障（[issue #119](https://github.com/hailingu/PlotWeave/issues/119)）：屏障覆盖画布防抖脏文档、项目保存链的失败重试登记与 AI 会话三类未落盘数据（画布与项目链部分见 §10.2），先等在途写入落定，每项目最多尝试一次失败快照；期间新加入的保存也需等待，仍失败则保留窗口并显示错误。启动间隙（原生退出屏障已安装、前端退出监听未注册）内到达的 ⌘Q/Dock 退出请求由 Rust 侧门闸缓冲；前端监听注册完成后经 `acknowledge_quit_listener` 确认就绪，确认消费暂存并重放一次同一 `app-quit-requested` 事件，使其进入同一冲刷屏障。暂存与直发互斥：被暂存的请求不再同时直发，同一退出请求至多投递一次，不形成并发双派发重复冲刷（[PR #82](https://github.com/hailingu/PlotWeave/pull/82)）；确认晚于注册保证重放必有接收者，就绪后到达的请求由已注册监听直接接收、不再缓冲（[issue #65](https://github.com/hailingu/PlotWeave/issues/65)）；前端持续未加载时退出请求仍会被取消，属记录在案的保留边界。原生退出回调自身的 panic 被遏制在 Rust 侧、不跨 `extern "C"` 边界 unwind（[issue #547](https://github.com/hailingu/PlotWeave/issues/547)）：按未知冲刷状态保守拒绝本次终止并输出稳定诊断码 `code=quit-callback-panicked`（不含 panic 载荷，与后台任务诊断同口径；stderr 不可写时诊断静默放弃，写失败不得产生新的越界 panic——[PR #580](https://github.com/hailingu/PlotWeave/pull/580) 评审），退出请求可重试。没有后台自动重试；强制终止后未保存内容可能丢失，不承诺跨进程恢复。

删除项目等待已有写入并清除项目目录中的会话，成功后清除内存快照；删除墓碑期排队的会话写入被吸收——不执行但按 id 留存最新写入，删除失败（项目仍在磁盘）时重排回吐（与画布保存同口径，[issue #59](https://github.com/hailingu/PlotWeave/issues/59)），补写自身失败时保留快照经失败事件交给 App 级恢复通道（重开项目时内存副本胜出并提示可重试，退出屏障仍兜底），删除成功则随项目一并丢弃，绝不重建已删目录；不再有恢复副本清理回执或首页孤儿副本扫描。复制项目仅复制画布和项目资产，不复制对话；现有剧本导出也不包含会话。
### 10.2 写入安全

单写者场景**不需要**文件锁、版本号等并发机制；但需要防崩溃截断——写到一半进程被杀、断电、磁盘满，会留下截断的 JSON，导致整个项目无法打开。因此：

- **控制文件信任链是所有 I/O 的前置条件**：Rust 先 canonicalize `app_data_dir` 为受信根；`projectId` 等路径分量先通过对应的文件名安全字符集校验，再参与拼接。对 `projects/`、`library/` 及目录化布局的 `projects/{projectId}/`，现存目录必须是实际目录且 canonical 路径逐级仍位于父级受信根内，任一级为符号链接（无论指向根内或根外）、非目录或无法验证都拒绝**整个对应操作**，不能只禁用其 `assets/`。缺失目录只能在已验证父目录下创建，创建后立即 canonicalize 复核。读取、创建、替换、删除或扫描 `project.json`、旧布局 `{projectId}.json`、`index.json`、`library/library.json`、`library/asset-delete-journal.json`、`library/asset-delete-archive.json`（#421 兼容迁移来源，仅删除日志为旧数组根或缺失时读取；咨询性异型告警按 0/未知继续，对象根日志落盘后不再读取或写入）、`settings.json` 及其临时文件前，使用 `symlink_metadata` 拒绝最终路径为符号链接，现存文件还须是普通文件且 canonical 后仍是已验证父目录的直接后代；目录扫描跳过并报告符号链接/越界项，绝不跟随。验证后保持父目录句柄打开，所有实际 open/create/rename/delete 均以平台等价的 no-follow、相对目录句柄语义执行，不得 canonicalize 后退回未经绑定的原字符串路径，避免检查与使用之间被替换。新临时文件以该目录句柄下的随机同目录名称排他创建，避免预置 `.tmp` 符号链接截获写入；最终 rename 前再次验证现存目标。该解析器由项目 list/create/load/save/delete/复制流程、布局迁移、索引校正及库/设置命令共用，验证失败时不得读取、写入、删除外部树中的文件，也不得先更新另一控制文件。
- **资产文件能力边界**：控制文件与资产文件共用“受信根句柄绑定、逐组件 no-follow、实际 I/O 不退回字符串路径”的底层解析器；控制文件按本节校验，项目/库资产的读、写、媒体响应与删除还必须执行 §7.1 的专用资产根规则。canonical 路径和已校验内存条目只能用于诊断或选择逻辑对象，不能代替实际文件句柄授权。
- 在目标文件的受信父目录句柄下排他创建随机同目录临时文件（如 `project.json.<随机值>.tmp`），写入并 flush 后以目录句柄相对 rename 覆盖 `project.json`（rename 原子，读者只见旧版或新版，不见半个文件）。`index.json` / `library.json` / `settings.json` 同样处理；不得使用可被提前布置的固定 `.tmp` 路径。
- **项目删除的持久性屏障**（[issue #591](https://github.com/hailingu/PlotWeave/issues/591)，已实现）：删除顺序保持不变——先按句柄相对 no-follow 递归移除资产树，再移除权威控制文件；资产树删除失败时项目记录仍在、可发现可重试，避免先删记录留下不可发现的孤儿媒体。两次移除都落定后、返回成功前，对锚定的 `projects/` 目录句柄自身执行 fsync（经 `open_dir(".")` 重新绑定句柄，不按路径名重开）；成功回执因此表示两个目录项的移除都已到达持久介质，成功返回后断电/崩溃不会复活“JSON 已删、资产树已落盘”的孤儿目录或“资产已删、JSON 保留”的媒体全丢项目。fsync 失败上浮为错误、不得报告成功：此时命名空间移除已完成，缺失目标被容忍，重试幂等并重新执行屏障。屏障在 projects 操作锁内执行，排队的保存不会越过它重写已删记录。成功返回**之前**的崩溃/断电仍可能留下部分移除状态（资产树移除已持久而记录未持久，或反之），命令不承诺未返回成功时的崩溃原子性；非 Unix 沿用目录句柄无法 fsync 的平台边界，不设屏障。
- **控制文件字节上限**（[issue #592](https://github.com/hailingu/PlotWeave/issues/592)，已实现）：单个项目控制文件（`projects/{id}.json` 与项目内 `ai-session.json`）的读取/写入上限为 **64 MiB**（`CONTROL_FILE_MAX_BYTES`，Tauri/Rust 与 Swift 原生共用同一额度）。读取先按 no-follow 元数据长度拒绝静态超限（打开前，列表持锁的最坏单文件工作与文件大小无关），文件在校验后增长时由 cap+1 流式限读兜底：最多物化上限+1 字节，超限在完整分配/解析前返回 `Limit` 诊断，原文件保持不动、不部分解析。列表把超限文件呈现为带诊断的损坏占位（不得静默跳过），`load_project` 返回可定位的 `Limit` 错误；保存侧在序列化后、落盘前按同一上限拒绝，保证“可读即可写回”，不会生成下次启动无法读取的文件。额度远高于正常短剧项目（含长篇设定文档）的规模，只拦截异常膨胀/损坏的单文件；项目媒体是独立文件，不套用该上限。列表仍在 `projects_op_lock` 内逐个读取/解析以保持单写者快照一致性；限读把单个坏文件的成本封顶，索引化/锁外列表是后续演进，不在本处置中承诺。

- **崩溃遗留临时文件的顺带清扫**（[issue #148](https://github.com/hailingu/PlotWeave/issues/148)，已实现）：进程在排他创建临时文件与 rename 之间被终止时，进程内的失败清理不会执行，留下无引用的随机 `.tmp`。`list_projects` 与 `list_library_assets` 顺带清扫各自目录（项目侧 `projects/` 根与 `projects/{id}/` 会话目录——[issue #722](https://github.com/hailingu/PlotWeave/issues/722) 在 Rust store 落地：列表在 projects 操作锁内遍历名字为合法项目 id 的真实目录，经 no-follow 归类与身份绑定逐目录以 `ai-session.json` 目标白名单执行同款清扫，不进入 `assets/` 等子目录；库侧 `library/` 根与 `library/assets/`，`assets/` 缺失或为符号链接时跳过且不在读路径创建）。条目须**同时**满足三条件才被移除：① 归属可辨——名字匹配本协议命名 `.{目标名}.{id}.tmp`（隐藏点前缀、`.tmp` 后缀），目标名落在本目录原子写目标白名单内（`projects/` 根仅 `{项目 id}.json`；`projects/{id}/` 会话目录仅 `ai-session.json`（issue #722，Rust 侧）；`library/` 根仅 `library.json`/`asset-delete-journal.json`/`asset-delete-archive.json`（仅兼容历史遗留临时文件）/`library-corrupt-<64 位摘要>.bak`；`library/assets/` 为 `{资产 id}.{1~8 位小写扩展名}`，资产 id 域含旧 `la-{ms}-{size}` 方案存量），且 id 段匹配防碰撞生成器的唯一产出形状 `p-<小写十六进制>-<小写十六进制>`（长度 ≤64；PR #217 两轮评审收紧——宽字符集与非空目标会把 `.notes.backup.tmp`/`.notes.p-18f-0.tmp` 之类外来文件误收误删；id 段长度不按 epoch 收窄，十六进制结构是稳定契约，长度随时间戳/计数/哈希漂移）；② 超龄且不活动——mtime 超过 24h 宽限期（临时文件正常生命周期为毫秒~分钟级，未来时刻的脏时间戳按未超龄保留），且清扫与本目录的原子写经进程内操作锁串行（`projects/` 锁由 list/create/save 内核持有——会话目录清扫与 `save_ai_session_file` 的原子写共用同一把锁，`library/` 由 §7.2 库操作锁覆盖；PR #217 第三轮评审——挂起恢复或时钟前跳使进行中写入的临时文件显得超龄时，清扫也无法插入排他创建与 rename 之间）；③ no-follow 归类为普通文件——符号链接与目录等异型条目只跳过、绝不跟随，移除只删目录项自身。清扫尽力而为、fail-soft：扫描/元数据/删除失败只留结构化诊断，不阻断列表/启动，也不因单条坏数据中断其余回收；只删除、不读取内容，遗留临时文件不充当恢复副本（不扩大为新的恢复副本协议）。剩余记录边界：跨进程并发实例写同一 `projects/` 树不在操作锁范围（§10.2 单写者模型，由前端保存链承担；库侧跨进程另有 §7.2 文件锁）；`projects/{id}/assets/`（项目媒体临时文件）与应用数据根（`settings.json` 及其损坏备份 `settings-corrupt-<摘要>.bak` 的原子写临时文件）暂不清扫，积累速率低，如需回收按同一内核扩展；Rust store 的 `projects/{id}/` 会话目录已由 issue #722 纳入清扫，原生 Swift 路径（`NativeProjectStore.listProjects`）仍只扫 `projects/` 根，其会话目录临时文件沿用本记录边界，待原生侧按同款内核补齐。
- `project.json` 是项目内容及合法 name/updatedAt 的权威真源，`index.json` 只是可丢弃、可重建的首页缓存；两个文件的独立 rename **不构成跨文件事务**。`create_project`/`save_project` 先原子提交项目文档，再以同一 name/updatedAt 更新索引。Rust 启动时、且最迟在每次 `list_projects()` 返回前，扫描项目文档（布局迁移期同时覆盖 §10.1 的旧路径回退），以受信路径 id 与文档中的合法 name/updatedAt 重建或校正索引：补缺失项、覆盖不一致项、移除已确认没有项目真源的陈旧项；缩略图等仅存于索引的展示字段只在对应项目仍存在时保留。文档元数据异型时不得把非法值写进索引：保留可用的合法索引回退，否则返回明确的损坏占位与诊断，留待 §11.1 加载归一化修复。校正后的列表直接从这份内存投影返回，并尝试以 tmp + flush + rename 回写索引；即使回写再次失败也不得返回已知陈旧的 name/updatedAt，须报告可恢复警告。由此在两次 rename 之间崩溃、索引写失败或索引损坏只会造成可恢复的缓存陈旧，不会让首页长期显示与项目文档不一致的名称或更新时间。
- 前端防抖窗口以 `SAVE_DEBOUNCE_MS`（定义于 `src/editor/useEditorPersistence.ts`，当前 600ms）为准，窗口内无新变更即提交一次；失败回队重试；`flushPersist()` 在关闭窗口/切换项目前调用。退出屏障同样等待防抖落盘（[issue #119](https://github.com/hailingu/PlotWeave/issues/119)）：编辑器挂载期间向应用级注册表（`canvasSaveRegistry`）登记「有脏或在途」探针与立即冲刷闸，退出冲刷先补交画布最新编辑，再处理保存链；失败重试登记（含未落定链上动作）在退出时立即重存，每登记至多尝试一次，代次已前进的陈旧登记不重放（新保存拥有终态，陈旧稿不得后完成覆盖新内容），仍失败则阻断退出、保留登记与 5s 后台重试节律并显示诊断。重试可以复用同一份序列化载荷，但其中的 `project.updatedAt` 不具有权威性：每次 `save_project` 尝试都由 Rust 在保存边界重新生成时间，调用方不得通过预先盖戳或重放旧值决定本次保存时刻。序列化时节点 `ui` 会话态（`selected`/`expanded`）按 §3 不落盘——`serializeProject` 输出统一重置为加载初值（`selected: false`、`expanded: true`），内存中的选中态不进入载荷；`update_node_ui` 不置脏（§9.4），纯选择/折叠操作不触发防抖保存，也不会因此刷新 `updatedAt` 改变首页最近项目排序。置脏判定的实现口径：前端以持久化签名（剔除 React Flow 会话态与样式类后的语义序列化）变化置脏；签名逐项按节点/连线对象身份缓存并按持久字段引用记忆（[issue #272](https://github.com/hailingu/PlotWeave/issues/272)，已实现）——拖拽过程帧只重新序列化被拖节点，无关重渲染零序列化；签名字面与整体序列化一致，置脏/防抖/失败重试/卸载与退出冲刷/aiRevision 提交对账契约不变。
- **画布冲刷结果（[issue #849](https://github.com/hailingu/PlotWeave/issues/849)）**：`flushPendingCanvasSaves()` 在冲刷落定仍脏时返回绑定 owner 与编辑水位的失败探针，否则返回 null；冲刷期间注销或替换的旧 owner 不再报告失败。退出屏障在同轮项目、AI 会话和设置冲刷后复核：同一 owner、同一编辑水位仍脏且尚未被项目重试清除时，即使其他失败列表为空也立即阻断并点名画布；仅成功冲刷后新增的工作进入下一轮固定点，不在失败状态热循环。脏文档、已有防抖重试、项目链重试登记与持久化覆盖通知仍由原 owner 管理，恢复后用户可重试退出。普通 `projectStore` 磁盘写失败本就登记项目重试；本修复补齐画布独立失败状态，不据此声称所有磁盘失败均曾导致挂起。
- 项目文档保存成功（含失败登记后的链上后台重试成功）即向前端发出落定通知（issue #101）：编辑器卸载冲刷/在途保存可以晚于返回首页的列表读取，首页摘要（名称、派生统计、更新时间/排序）靠该通知在导航读取之后再刷新一次，恢复到与磁盘一致；保存失败不发出通知，且失败按磁盘状态分两类（§10.5 保存边界同款分类）——**提交前失败**（信封/资产预验、临时文件创建/写入/同步或 rename 失败）磁盘保持旧内容，首页不得虚报新摘要；**提交后失败**（`atomic_write` 的 rename 已成功但目录 fsync 持久性屏障失败，或写后资产复验拒绝）时 `projects/{id}.json` 已被新内容替换并带新盖戳，但不发通知，首页可能继续显示旧摘要，直至下一次挂载/回到首页/后续保存成功触发的列表重读。首页并发发起的多次列表读取按发起序收敛，较旧的响应不得覆盖较新的结果。
- 首页列表的维护写与普通保存共用同一项目保存链（[issue #134](https://github.com/hailingu/PlotWeave/issues/134)，已实现）：空库播种先等该 id 在途保存落定再探测（在途链落定不改链身份、身份守卫看不见；等落定后探测，保存所建文件经「项目已存在」自然跳过），仅在 `load_project` 确证「项目不存在」后经链写入（no-replace 语义不变——文件存在含不可读一律跳过），探测窗口内目标示例的删除在途时种子写被删除墓碑吸收、不为删除中项目落盘，目标存在保存失败的重试登记（最新未落盘内容比磁盘/空目录新）或探测窗口内排入新写入（链身份变化，探测结果已过时）时同样跳过种子写——成功的种子写会清除登记或以硬编码内容覆盖窗口内写入，留待链重试交付；已知示例的修复回写先等该示例保存链静止再读盘，读盘/资产复验的 await 窗口内该示例排入新保存或删除（链身份变化）即跳过本次回写——迟到修复不得覆盖较新内容或复活已删对象，留待下次列表/打开重查；链上存在保存失败的重试登记（最新未落盘内容比磁盘新）同样跳过回写——成功保存会清除登记、永久丢弃该内容，留待链重试交付；回写失败由链登记重试并经落定通知刷新首页。

#### 设置保存状态与不变量（issue #121）

[issue #121](https://github.com/hailingu/PlotWeave/issues/121) 已实现：`save_prefs` 的设置层负责序列化、1 MiB 上限与应用数据根句柄，复用 `store::atomic_write` 完成控制文件替换及持久性屏障。数据目录的创建（设置读取与保存入口共用 `ensure_data_dir` 内核）经 `store::create_dir_all_durable` 持久化完成（[PR #201](https://github.com/hailingu/PlotWeave/pull/201) 三轮评审修订，Unix）：创建时刻探测最深已存在祖先，新建目录条目所在的各级宿主（自锚点至直接父目录）在写入任何内容前逐级 fsync——首启读取（`load_prefs`）与首次保存创建的条目均与内容同为持久。创建或同步失败时，内核尽力自深至浅拆除本次新建的层级（仅空目录可拆）后返回原错误，重试得以重新探测锚点、再做全链同步，而非退化为「目录已存在」的单级兜底。目录已存在时保存仍兜底同步其直接父目录一次（单级防御）。剩余边界：清理前来不及执行的崩溃／断电、清理不完整（并发写入占据层级）与并发调用方在创建与同步之间进入，均残留多级未同步状态并由下次调用的单级兜底承接——需要「多级新建 + 精确崩溃窗口 + 其后断电」三重叠加，按 P2 记录在案。store／library 侧创建入口已接入同一持久化契约（[issue #309](https://github.com/hailingu/PlotWeave/issues/309)，已实现）：`projects_dir`／`library_root` 的应用数据根走 `create_dir_all_durable`；句柄相对的 `ensure_projects_dir`、`ensure_library_dir`、`assets_root`、资产 `ensure_child_dir` 与项目会话目录创建在本次真实创建条目后经 `sync_new_child_dir_host` 同步宿主（句柄相对 `open_dir(".")` 转标准句柄 fsync，不按绝对路径重开以保持 §10.2 信任链），失败拆除重建；已有目录（AlreadyExists 容忍路径）的条目持久性归创建时刻的调用方负责，不重复同步。所有设置保存入口均经同一内核；不改变整份保存的 IPC 协议、设置读取失败策略或前端保存排序。旧 `settings.json.tmp` 占位无需删除，也不会被本次保存改写。

[issue #390](https://github.com/hailingu/PlotWeave/issues/390) 已实现（覆盖前损坏备份）：残余窗口是成功加载之后 `settings.json` 被应用外部破坏（加载期保护由 issue #120 的 ready 门控承接），任意一次防抖落盘或关闭冲刷会不可逆覆盖损坏原件、`keyEnc` 密文随之消失。该覆盖路径现接入 `store::damaged_backup` 共用内核（自图库 #137 处置提取，图库侧同改走该内核、语义不变）：相对锚定句柄对既有 `settings.json` 做 no-follow 归类 + cap+1 限读——条目缺失视为无原件可保护（不备份），符号链接/非普通文件/超限按备份异常拒绝；字节解析为 JSON **对象**即健康直接放行，其余（非法 JSON、合法但非对象、非法 UTF-8）按**原字节**在同目录耐久备份为 `settings-corrupt-<SHA-256 摘要>.bak`。同摘要有既有备份时，校验普通文件身份（Unix 按 (dev, ino) 绑定）与完整字节并重新同步后才复用——失败重试不累计相同副本，原件变化保留独立备份；备份创建、读取或同步失败（或同名备份类型/内容不符）阻止本次保存并上抛「备份损坏设置原件失败：…」类可诊断错误，不执行覆盖；备份成功后才照旧执行 §10.2 原子覆盖。备份临时文件命名沿用 `.{备份名}.{id}.tmp` 协议；应用数据根暂不清扫遗留临时文件（含备份临时文件，见上文记录边界）。跨进程并发写同目录不在设置写互斥范围（§10.2 单写者模型记录边界）。

[issue #436](https://github.com/hailingu/PlotWeave/issues/436) 已实现（Unix 凭据文件私有权限）：设置保存和旧密文迁移共用 `atomic_write_private`，临时 inode 以 `0600` 创建（umask 可进一步收紧），原子 rename 后设置沿用该权限；设置损坏备份同样私有创建。复用既有备份在身份与原字节校验后，通过文件句柄收紧权限，再同步文件和目录；收权失败继续由既有备份错误出口阻止覆盖。其他控制文件的默认权限与 I/O 顺序保持不变。不自动遍历历史文件收权，非 Unix 不实现 POSIX mode；[权限状态矩阵及验证边界](provider-settings.md#凭据文件权限状态与不变量issue-436)记录两条设置写入口、临时文件暴露窗口与备份失败重试。

[issue #435](https://github.com/hailingu/PlotWeave/issues/435) 已实现（超限后的人工恢复指引）：`load_prefs` 发现磁盘文件超过 1 MiB，以及 `save_prefs` 的覆盖前备份失败时，诊断保留原失败原因并显示实际 `settings.json` 路径。条件式重建指引要求先退出应用、自行备份原件，确认不再使用原配置后才移走或删除该文件；重新打开应用时，文件缺失才由前端补默认设置，原 provider 配置与 API key 需重新填写并保存。备份失败出口统一附加该指引，不依赖错误文案猜测失败类别；权限或备份证据异常仍需按原原因处理，重建说明不保证修复目录权限等环境问题。超限原件继续经 cap+1 限读拒绝，不部分解析、自动备份、覆盖或删除；未增加应用内重置命令。默认设置只在缺失读取后进入内存，用户重新配置并保存时才写入新文件。

[issue #391](https://github.com/hailingu/PlotWeave/issues/391) 已实现：`load_prefs`／`provider_secret` 的读取路径与保存路径采用同一套文件系统边界——经共用的 `ensure_data_dir` 定位并持久化确保数据目录后，以共用的 `open_prefs_root`（canonicalize + `open_ambient_dir`）锚定受信句柄，对 `settings.json` 先做 no-follow 归类（符号链接与非普通文件在打开前拒绝——FIFO／目录等异型条目不会阻塞 blocking 池线程，符号链接不被跟随读取），再相对句柄打开并做身份绑定（Unix 按 (dev, ino) 与归类元数据比对，与 `store::persist::read_verified_file` 同法；非 Unix 无身份可比，打开后重走归类复核），最后经既有 cap+1 流式限读（issue #147）物化。归类拒绝与替换拒绝都不是 NotFound，不落入首启空对象语义（issue #120）；`provider_secret` 对二者维持读取失败的钥匙串只读回退（超限仍硬拒绝）。缺失／损坏／超限的读取失败分类语义不变。

### WebKit 请求信封的嵌套边界（issue #863）

`HostCommandRouter.handle` 将 WebKit body 序列化为 UTF-8 后，在 `HostRequest` 的递归 Codable 解码及请求身份登记前复用 `HostJSON.rejectNestingBeyondLimit`。整个信封最多 32 层，包含信封根对象与 `args` 对象；超限返回既有 `PW_INVALID_REQUEST`，不执行宿主服务，也不占用去重身份，因此同身份的合法重试仍可执行。字符串中的括号、引号转义不计为结构深度。该入口与项目文档共享深度上限；其余已记录的小载荷入口边界保留。
